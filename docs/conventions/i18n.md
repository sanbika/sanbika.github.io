# Internationalization (i18n) Conventions

This repository is built on Hugo + PaperMod and serves `zh-cn` (default) / `en`. This file collects the stable conventions that have emerged while maintaining both languages. Learned from the 2026 i18n wrap-up round (search title / Giscus language / switcher labels / English pages / site-level i18n copies).

## 1. Content pages

- **The content language of a page is the author's decision per page — a single-language page is a normal state.** The reality in this repository is: reading notes are mostly written in Chinese, occasionally in English from the start; full bilingual coverage is not a goal — do not translate a page just to complete a pair, single-language is the norm.
- **The `.en.md` pairing is for pages that genuinely need both languages** (e.g. `about/` — `content/about/index.md` + `content/about/index.en.md` — and the archive pages, `content/quests/<date>.md` + `<date>.en.md`). Once a page is judged bilingual, a new content page must ship both: the Chinese primary version (`xxx.md`) and the English mirror (`xxx.en.md`), with the front matter fields matching one to one (`title` / `date` / `draft` / `description` / `weight` / `comments` / …). The slug is assigned automatically by Hugo according to `defaultContentLanguageInSubdir`, so the two versions never collide (the Chinese default sits at the root, e.g. `/about/`, and the English mirror at `/en/about/`).
- **The language-dependent front matter values are written per language.** The archive pages are the clearest example: both versions carry the same field set, but the values differ where the language does — the `title` and `description` are written separately for zh and en, while `spark_date` and `discussion` stay identical across the two versions. A field whose value is language-dependent must never be hard-coded to one language.
- **UI pages** (e.g. `content/search.md`) follow the same bilingual convention, but **carry no hard-coded body text** — they only declare `title` and `layout`, and the matching template renders the content.

## 2. UI copy

- **Every user-visible string must come from `i18n/<lang>.yaml`; never hard-code it in a template.** A hard-coded string leaves the source-language copy behind when the language is switched.
- **The site-level i18n copy** (the repository root `i18n/zh-cn.yaml`) exists to override the theme's default translations and to keep the fallback chain from breaking on a theme upgrade. It must be **byte-identical** to the theme source `themes/PaperMod/i18n/zh.yaml` (apart from the file header comment). Any deviation must be declared in the file header with a note describing the synchronization strategy (e.g. the snapshot scope and the fields that deliberately differ), otherwise a `diff` during a theme upgrade reports a false conflict.
- **The theme submodule's `i18n/*.yaml` files are upstream sources — do not edit them directly.** To change theme copy, override it in the repository root `i18n/<lang>.yaml`.

## 3. Third-party component language

- When integrating giscus / disqus / algolia and similar third-party components, **do not hard-code the language code as "if it is en then X, otherwise Y"**. That pattern is a trap for a future third language (every non-en language falls through to Y, and the component renders in the wrong language).
- The recommended form is `cond (eq .Lang "en") "en" .Lang`, provided the value is an enumeration of the language codes the component supports. If the component does not support some language codes, enumerate them in an `if-else` chain down to a default, and note the supported range in the file header.
- **Both giscus partials follow one unified rule now**: `layouts/_partials/comments.html` and `layouts/_partials/spark_comments.html` both write `cond (eq .Lang "en") "en" (default .Lang .Site.Language.LanguageCode)`. English is forced to `en` (giscus is case-sensitive). For every other language the **site-level** `languageCode` is what gets emitted and the page-level `.Lang` is only the fallback — Hugo's `default` returns its **second** argument when that argument is non-empty, so `default .Lang .Site.Language.LanguageCode` means "use `LanguageCode`, fall back to `.Lang`". That order is the correct one here: the site-level `languageCode` is the code giscus recognises (`zh-CN`, case-sensitive), while the page-level `.Lang` is only the lowercased language key (`zh-cn`), which giscus does not recognise and which silently falls back to the English UI. See [[conventions/giscus.md]] §5.

## 4. Configuration files

- The `languageName` field in `config/_default/languages.toml` is the legacy spelling of `label`. Both `zh-cn` and `en` already use `label`, so the field does not appear in the config at all. (It is not "removed" — Hugo v0.164.0 still reads it and still lets `.Language.LanguageName` return it, it just emits no warning and does nothing when `label` is also present.)
- **Hugo v0.158.0 renamed three language config keys and three language methods.** Config: `languageCode` → `locale`, `languageName` → `label`, `languageDirection` → `direction`. Methods: `.Language.LanguageCode` → `.Language.Locale`, `.Language.LanguageName` → `.Language.Label`, `.Language.LanguageDirection` → `.Language.Direction`. The build currently emits **three** deprecation warnings, and they do not all come from the same place:
  - `languages.zh-cn.languageCode` — from `config/_default/languages.toml` (the repo's own config).
  - `.Language.LanguageDirection` — from the **theme's** `themes/PaperMod/layouts/baseof.html`.
  - `.Language.LanguageCode` — from the **theme's** `themes/PaperMod/layouts/_partials/templates/opengraph.html`, and from the repo's own three call sites (`layouts/_partials/comments.html`, `layouts/_partials/spark_comments.html`, `layouts/_default/rss.xml`). Hugo prints the message once per build, so the theme and the repo share that single line.
- **The `languageCode` → `locale` migration is deferred on purpose, and it is safe whenever it is done.** The repo keeps `languageCode = "zh-CN"` because that exact string is the code giscus recognises (it is case-sensitive; an unrecognised code silently falls back to the English UI). The migration does **not** force a change to the giscus partials: `Language.LanguageCode()` transparently falls back to `Locale()`, and `Locale()` falls back to `LanguageCode()` and then to the language key. Verified on Hugo v0.164.0 — a site configured with only `locale = "zh-CN"` still returns `"zh-CN"` from `.Site.Language.LanguageCode`, and the rendered `data-lang` and RSS `<language>` values are unchanged.
- **What actually blocks the migration is the theme, not the repo.** The repo's own three call sites can be switched to `.Language.Locale` at any time — that is the cheap half. The two theme-side warnings can only be silenced by copying `baseof.html` and `_partials/templates/opengraph.html` into the repo's `layouts/`, which permanently diverges from upstream and makes `theme-drift-check.yml` report a diff on every theme upgrade. So the migration is worth taking as one piece, or not at all — and today three lines in the build log are cheaper than a permanent fork of the theme.
- `config/_default/params.toml` and `config/_default/config.toml` **must not define the same `[params]` field**. New parameters all go into `params.toml`, to avoid duplicates (see the TODO in [[current-state.md]]).
