- **The check-in thumbnails are served from the site itself (2026-10-22)** `fix: serve the check-in thumbnails from the site instead of GitHub's CDN`
  - **User pain point** (why this had to change): the thumbnails on the home page sidebar and on the archive pages were **broken images**. The markup was fine and the URLs were fine — the photos loaded with HTTP 200 — but they took seconds to arrive, and on the reporter's network they never arrived at all, so the browser drew the broken-image icon.
  - **Root cause**: the `<img>` pointed straight at `image_url`, which is GitHub's attachment CDN URL. That URL 302-redirects to an S3 bucket and serves the **full-resolution original** — and one of the four photos is a **3060×4080, 2.65 MB phone photo**. So a 28×28 sidebar thumbnail was downloading 2.6 MB from a third-party host, and the home page alone pulled ~2.9 MB of photos. On a slow, filtered or cross-border path that request times out and the image never paints.
  - **What changed**:
    - **The photos are now in the repository**: `assets/img/checkins/<date>.jpg`, pre-shrunk to ≤800px wide (800×600 / 800×1067 / 800×1067 / 800×182 — 259,776 bytes for all four, versus 3,152,271 bytes of originals).
    - **`layouts/_partials/checkin_image.html` is the one place that renders a check-in photo.** It hands the local copy to Hugo's image pipeline and asks for a square WebP at 2× the CSS size (`Fill "<2*size>x<2*size> center webp q80"`), which reproduces the `object-fit: cover` crop in the browser at retina sharpness. The three call sites — the 28px sidebar thumbnail, the 64px list thumbnail and the 96px detail thumbnail — all go through it.
    - **`data/spark_checkins.json` carries both paths**: `image_url` stays the remote original (source of truth, and the fallback when a local copy is missing), `local_image` is the new path of the repository-local copy.
  - **Key decisions**:
    - **The originals stay off the repository on purpose.** Only ≤800px copies are committed: the site never displays anything larger than a 192px crop, so committing a 2.6 MB phone photo would be dead weight. The full-resolution original still lives on GitHub's CDN and stays reachable through the discussion comment link next to every thumbnail — the "photos live on GitHub, the site is only a viewer" property is unchanged, the site simply no longer *depends* on that host at render time.
    - **The site no longer has a third-party image dependency.** This is the point of the change: a thumbnail that comes from another origin can be blocked, filtered, throttled or slow, and the reader gets a broken image. A crop served from the site's own origin cannot fail that way.
    - **WebP at 2× the CSS size.** The 2× factor is what keeps a thumbnail sharp on a retina screen; WebP keeps the payload in the low kilobytes (682–4,616 bytes per file) instead of the tens of kilobytes a JPEG crop would cost.
    - **The fallback path is kept.** A check-in without a `local_image` still renders through the remote `image_url`, so adding a photo without committing it does not break the page — it only makes it heavy.
  - **Verification**: `hugo --minify --gc --buildFuture` passed — **25 ZH / 23 EN pages**, no build error, and the built pages now reference only local WebP crops (`/img/checkins/2026-08-24_hu_….webp` and friends) instead of `github.com/user-attachments/...`. The image payload per page: home page **2,156 bytes** (was ~2.9 MB), archive list **7,808 bytes** (was ~3.15 MB), single-day page **3,880 bytes** (was 200 KB for that day alone). The 12 crops the build emits are 682–4,616 bytes each. The comment threads and their photos are untouched — the giscus discussion still renders both of the 2026-08-24 comments with the full-size picture inside the thread.
